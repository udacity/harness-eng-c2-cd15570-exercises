# Module 2 Demo: Loading Incident-Response Skills on Demand

This demo shows how an AI agent can load detailed domain instructions only when
they are relevant to the current request.

## Use case overview

The demo continues the `INC-2048` incident from Module 1. An online store's
production `checkout-api` became degraded after `checkout-v42`, and the checkout
error rate is 18 percent. The team still needs to diagnose the problem, consider
safe remediation, and communicate accurately with stakeholders.

Those tasks require different kinds of guidance. A diagnostic request needs
triage and service-runbook instructions, while a stakeholder update primarily
needs communication guidance. An end-to-end response may need all available
skills.

The demo compares two ways of supplying that guidance:

| Mode | Flow | What it demonstrates |
| --- | --- | --- |
| `basic` | Load all four complete skills → write in one LLM cycle | Eager context is simple, but every request receives every skill. |
| `skills` | Show names and descriptions → select and load relevant skills → write in a second LLM cycle | Progressive disclosure reduces irrelevant context but adds a model cycle. |

Skills in this demo are Markdown instruction files. Loading a skill gives the
model specialized guidance; it does not restart a service, perform a rollback,
or mutate production.

The goal is not to prove that one mode always writes a better response. The
demo makes context selection, loaded instructions, model cycles, tokens,
latency, and evaluated output visible so the two designs can be compared.

## Shared incident

The immutable incident is stored in
[`data/incident.json`](data/incident.json). It represents a ticket generated by
an upstream incident system outside the agent loop. Both modes receive the same
ticket and service the same request.

```text
Incident:               INC-2048
Environment:            production
Service:                checkout-api
Incident status:        INVESTIGATING
Current deployment:     checkout-v42
Last-known-good:         checkout-v41
Service health:         DEGRADED
Checkout error rate:    18%
Restart performed:      false
Rollback performed:     false
Recovery confirmed:     false
Authenticated user:     Sam Rivera, support_engineer
```

The deployment occurred before the error increase, but that timing does not
prove root cause. The agent must not claim that a restart, rollback, recovery,
or resolution occurred.

## Incident requests

The `requests/` folder contains three tasks over the same incident:

| Request | Operator need | Expected relevant skills |
| --- | --- | --- |
| `checkout_diagnosis` | Produce an internal triage note with the next diagnostic checks | `incident_triage`, `checkout_service_runbook` |
| `stakeholder_update` | Give stakeholders an accurate current update | `incident_communications` |
| `incident_response` | Combine diagnosis, safe remediation planning, and communication | All four skills |

Every final note must:

- contain exactly 60 whitespace-separated words;
- include `INC-2048`;
- use only confirmed incident facts;
- distinguish facts from hypotheses;
- avoid claiming an action or recovery that has not occurred; and
- give a useful next step.

The `expected_skills` values are a teaching benchmark. The terminal reports
whether selection matched them, but final-answer acceptance comes from the
separate evaluation boundary.

## Available skills

| Skill | Detailed guidance it provides |
| --- | --- |
| `incident_triage` | Evidence gathering, hypotheses, unknowns, and next diagnostic checks |
| `checkout_service_runbook` | Checkout health, deployment history, logs, and failure isolation |
| `safe_remediation` | Safe restart or rollback planning, authorization, and verification |
| `incident_communications` | Accurate internal and stakeholder incident updates |

Each `SKILL.md` contains short YAML frontmatter followed by its detailed body.
During routing, `catalog.py` reads only the skill name and description. The
complete file is loaded in `skills` mode only after the model requests its exact
allowlisted name through `load_skill`.

## Run the LLM-backed classroom demo

Install the dependencies:

```bash
cd module-2-skills/demo
python3 -m pip install -r requirements.txt
```

Add a current course API key to `.env`. Run each request separately with:

```bash
python3 main.py compare --request checkout_diagnosis
python3 main.py compare --request stakeholder_update
python3 main.py compare --request incident_response
```

Or run all three requests together with:

```bash
python3 main.py compare --request all
```

The demo uses `gpt-4.1-mini` through the course endpoint. Every run waits for
Return after each serving-model cycle and saves the terminal output under
`output/`.

Skill selection and prose vary. A model may omit a relevant skill, load an
unnecessary skill, or produce a worse response with less context. Treat the
observed result as evidence rather than forcing a preferred outcome.

## What happens in `basic`

`run_basic()` eagerly reads all four complete `SKILL.md` files and inserts them
into one prompt, even when the request needs only one skill:

```text
base instructions
      +
all four complete SKILL.md bodies
      +
incident facts and operator request
      ↓
one LLM call
      ↓
final incident note
```

This path is easy to understand and requires one model cycle. Its tradeoff is
that every request pays for every skill, and unrelated guidance competes for the
model's attention.

## What happens in `skills`

The on-demand path uses two model cycles:

```text
Cycle 1: select and load

base instructions + skill names/descriptions + incident request
                              ↓
                    load_skill calls
                              ↓
harness validates each exact name and returns complete skill text

Cycle 2: write

previous_response_id=selection.id + function_call_output items
                              ↓
                  tools are not offered again
                              ↓
                    final incident note
```

The harness treats the catalog as an allowlist. Unknown skill names, malformed
JSON, extra arguments, and unsupported tools become controlled `ERROR` tool
results rather than filesystem paths. If the model selects no skill, cycle 2
still asks it to produce the final response.

## Evaluation boundary

After either serving path produces a note, `evaluator.py` applies the Module 1
evaluation pattern:

- Python checks the exact 60-word count.
- Python checks for the exact `INC-2048` identifier.
- A fresh LLM conversation judges factual grounding.
- The fresh evaluator judges whether the next step is useful and safe.

The final note passes only when all four criteria pass. Missing or malformed
named evaluator decisions fail closed.

Evaluator calls are experiment overhead rather than part of the `basic` or
`skills` serving design. Their tokens and time are printed separately and are
excluded from the serving comparison table.

## Conversation and tool boundaries

The live paths call `client.responses.create(...)` directly:

```text
Basic writing:       no previous_response_id; all skill bodies in instructions
Skill selection:     no previous_response_id; load_skill tool is available
Skill-based writing: previous_response_id=selection.id; tool outputs supplied;
                     load_skill is no longer available
Independent review: no previous_response_id; candidate and facts supplied fresh
```

Continuing from `selection.id` lets cycle 2 retain the request and selection
context. Removing the tool prevents repeated skill-loading cycles. Starting the
evaluator fresh keeps its judgment outside the serving conversation.

## What to show during the demo

1. Open one `SKILL.md` and distinguish its short routing description from its
   detailed instructions.
2. Show that all modes receive the same immutable incident and operator request.
3. Run `basic` and point out that all four complete skills enter one prompt.
4. Run `skills` and show that cycle 1 initially receives only the catalog.
5. Follow each `load_skill` call to its validated `function_call_output`.
6. Show that cycle 2 continues from `selection.id` without offering tools again.
7. Compare loaded skill characters, API tokens, model time, and evaluation.
8. Run `stakeholder_update` to show narrow selection and `incident_response` to
   show multiple skills composed for one response.

## From this demo to the exercise

The exercise changes the domain from incident response to InspectAI marketing,
but the implementation has the same shape:

| Demo implementation | Exercise work |
| --- | --- |
| `catalog_prompt()` | Build one name/description line per skill without loading bodies |
| `SKILL_TOOL` | Define the strict `load_skill` function schema |
| `build_selection_instructions()` | Combine base instructions with only the short catalog |
| `resolve_skill_call()` | Parse, allowlist, load, and return a `function_call_output` |
| `write_with_skills()` | Continue from `selection.id` without offering tools |
| `run_with_skills()` | Connect selection, loading, writing, pauses, and metrics |
| Editing a `SKILL.md` body | Change detailed guidance without changing routing code |

The exercise has six marketing skills and six campaign briefs. This demo has
four incident-response skills and three requests. Both compare an all-skills,
one-cycle baseline with a two-cycle progressive-disclosure path, and both must
handle the no-skill case successfully.

## Deterministic tests

```bash
python3 -m unittest discover -s . -p 'test_*.py'
```

The tests require no API key. They cover incident and request loading,
catalog-only routing, the strict tool schema, exact allowlisting, malformed
calls, eager context, selective loading, tool removal in cycle 2, no-skill
completion, exact 60-word output, and evaluator-overhead separation.
